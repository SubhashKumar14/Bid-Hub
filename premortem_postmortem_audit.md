# BidHub Premortem and Postmortem Audit

**Scope:** Current repository checkout, tracked manifests/configuration, route handlers, schemas, frontend callers, test scripts, and recent Git history. Secrets and .env values were not read or reproduced. Findings marked **confirmed** come directly from current code; behavior requiring configured services is identified as unverified.

## Executive summary

The current checkout contained a confirmed payment signature bypass, silent simulated Razorpay credential fallback, unstable JWT fallback, and payment operations not consistently scoped to the authenticated client. The payment verification bypass was introduced in the latest commit (a3bce22). Production configuration also did not declare Razorpay credentials, and uploads silently used local disk if Cloudinary was absent.

The fixes in this change remove the Razorpay mock path, fail startup on missing critical production configuration, scope payment actions to the client owner, validate webhook metadata against the ledger, secure the non-production mock flow, correct the seed ledger state, bound GitHub import input/timeouts, update vulnerable dependencies, and add Razorpay signature tests. The production build, new signature suite, existing API workflow suites, and final dependency audits passed. Browser UI E2E could not be completed because the browser control safety check could not determine the current page URL. See remediation_report.md for exact commands and limits.

## Prioritized confirmed findings

### Critical

1. **Razorpay signature bypass.** backend/payments/RazorpayProvider.js, verifySignature: signature_simulated and placeholder keys returned success before production checks; production had a second unconditional bypass. Any signed-in caller could attempt to turn a fabricated payment into an assignment. **Reproduce:** instantiate with a placeholder key or send POST /api/payments/verify using the literal simulated signature. **Fix:** require configured Razorpay credentials, remove simulated order creation, validate gateway ID shape in production, and compare HMAC bytes with timingSafeEqual.
2. **Production payment fallback.** backend/payments/index.js, getPaymentProvider: absent Razorpay credentials silently selected a simulated Razorpay provider. backend/payments/RazorpayProvider.js, createCheckout, generated local mock order IDs. **Impact:** deployment could report escrow funded without a gateway transaction. **Fix:** require Razorpay keys unless PAYMENT_PROVIDER=mock is explicitly selected outside production; prohibit placeholder values and mock production mode.
3. **Unstable production JWT secret.** backend/index.js generated a new random secret at each boot when missing/placeholder, invalidating sessions across restarts and allowing a deployment to appear healthy with broken authentication. **Fix:** require a stable secret of at least 32 characters and fail startup otherwise.
4. **Payment endpoints lacked owner/role checks.** backend/routes/payments.js, /verify, /cancel, and /simulate-payment: verification and cancellation were only authenticated, with cancellation able to reopen a project using an unowned project ID; simulation was public in non-production. **Fix:** require client role and match the payment ledger to the authenticated client; simulation also requires the explicit mock provider and owner token.

### High

1. **Known vulnerable locked dependencies.** Initial npm audit reported 15 root advisories (3 critical, 7 high, 5 moderate) and 8 backend advisories (1 critical, 3 high, 4 moderate). Direct ZIP dependency adm-zip included critical archive resource risks; axios, mongoose, and transitive packages also had advisories. **Fix:** moved adm-zip to 0.6.1 and applied npm audit fix to both lockfiles. Final npm audit summaries report zero advisories in both trees.
2. **Webhook trusted signed order notes without comparing all values to the pending ledger.** backend/routes/payments.js, /webhook, and backend/payments/RazorpayProvider.js, verifyWebhook: event metadata supplied the project, client, student, bid, and amount used for assignment. **Impact:** a correctly signed but mismatched order metadata record could be applied to the wrong pending checkout. **Fix:** compare order/payment IDs, captured status, currency, amount, project/client/student/bid, and amount to the local pending ledger before accepting.
3. **Production upload durability depended on optional Cloudinary settings.** backend/config/cloudinary.js silently selected local disk storage when Cloudinary was missing. On ephemeral hosts uploaded work could disappear after restart. **Fix:** production now requires Cloudinary; local disk remains available for non-production.
4. **No configured Razorpay deployment values.** render.yaml did not declare PAYMENT_PROVIDER, Razorpay key ID/secret, or webhook secret. The prior credential fallback masked this omission. **Fix:** deployment manifest now requires these values as unsynced secrets; set them to Razorpay Test Mode values for the requested demo.

### Medium

1. **GitHub import accepted loosely parsed URLs and had no outbound timeout.** backend/routes/imports.js, /github: regex extraction could accept host/path confusion, and two axios calls could wait indefinitely. **Fix:** exact HTTPS github.com/owner/repo validation, optional bearer token, and 8-second request timeout.
2. **Seeded review balance used an invalid ledger status.** backend/seed.js created PaymentLedger.status = PENDING, outside the schema enum in backend/models/PaymentLedger.js; submitted milestone funds were omitted from pending review totals. **Fix:** seed now uses PENDING_REVIEW.
3. **Global JSON parser accepted 10 MB for all API routes.** backend/index.js applied the limit to ordinary JSON writes. **Fix:** JSON and URL-encoded limits reduced to 2 MB; ZIP uploads remain on their dedicated multipart path.
4. **Funded bid and milestone totals could diverge.** backend/routes/payments.js previously funded the bid amount while processBidAcceptance allocated each milestone's posted amount, without requiring the totals to agree. This could make escrow allocations larger or smaller than the captured order. Checkout now requires at least one milestone and equality to the bid total before changing the project state; the payment-flow suite covers rejection.
5. **Currency representation is inconsistent.** backend/models/Bid.js stores amounts as strings while milestones and ledgers use numbers. backend/routes/payments.js parses bid values before checkout. Currency values with decimals and formatting should be normalized to integer paise before expanding real payment behavior; no broad data migration was attempted.

### Low / maintainability

1. Generic stripe* ledger fields are reused for Razorpay order/payment IDs (backend/models/PaymentLedger.js, backend/payments/RazorpayProvider.js). This is confusing but a schema rename needs migration planning.
2. Frontend dashboards poll on intervals (Browse.jsx, ProjectDetail.jsx, ClientDashboard.jsx, StudentDashboard.jsx; chat polls at 5 seconds). This is a scale concern, not evidence of a current demo blocker. Visibility-aware polling or server events can be considered later.
3. **Documentation mismatch found and corrected.** At audit time, README.md described a simulated-only payment setup while the UI and backend included Razorpay. The README and deployment setup now describe Razorpay Test Mode and required production secrets.

## Premortem scenarios

| Scenario | Failure mechanism and impact | Detection | Recovery and regression coverage |
|---|---|---|---|
| Registration/login, expired JWT, logout, refresh | Missing/unstable JWT_SECRET makes tokens invalid after restart; frontend stores token in localStorage. | Login plus /api/auth/me before/after backend restart; inspect 401s. | Keep one stable secret, re-login on expiry. Startup validation is fixed; auth refresh still needs an integration run. |
| Guest or wrong-role access | Public routes are intended for browsing; protected routes depend on protect and requireRole. Payment endpoints previously omitted role/owner scope. | Call payment verification/cancel/simulation as a student and as another client. | Server-side 403/404; payment ownership checks added and integration coverage confirms student and unrelated-client cancellation is blocked. |
| Missing env, MongoDB, Cloudinary, Razorpay outage | Before fixes, generated JWT/mock credentials hid missing configuration; production upload fallback loses files. | Startup logs and health endpoint; verify DB readiness and a real upload. | Required JWT/MongoDB/Razorpay/Cloudinary now fail safely. MongoDB and gateway outage recovery remain deployment concerns. |
| Concurrent student bids | Unique project/student index prevents duplicate bids by one student; competing students can both bid while project remains open. | Submit concurrent bids and inspect counts. | Expected multiple pending bids; acceptance should choose one atomically. Existing test coverage is not yet executable here. |
| Duplicate accept / checkout / payment verification | Project transition uses atomic findOneAndUpdate; checkout can invalidate previous pending sessions. Parent ledger and project changes are not a database transaction. | Replay verify/webhook and compare project and ledger state. | Project compare-and-set blocks duplicate assignment. Regression tests added for signature rejection; DB-backed concurrency remains unverified. |
| Cancelled/interrupted checkout | Cancel can race with successful gateway payment; a lost browser callback relies on webhook, and there is no reconciliation job. | Cancel after payment, interrupt callback, replay webhook; compare gateway dashboard to ledger. | Webhook can complete pending checkout; stale or already-cancelled paid orders require operator reconciliation. Never mark funds settled from frontend state. |
| Milestone submit/revision/approval/completion | Route checks submission/ownership; milestone state changes are atomic, but ledger and notification writes are multi-step and not transactional. | Exercise submit → request changes → resubmit → approve all milestones. | Retry from dashboards; inspect ledger if a write fails mid-flow. Existing runtime script covers the happy/revision flow but needs MongoDB. |
| Notification dismissed/missing | Notifications are persisted and dashboards reload data; polling may delay updates. | Compare notification API with dashboard after role switch/reconnect. | Recover from dashboard and notification list; no realtime delivery guarantee. |
| Back/forward, trailing slash, deep link | Vercel rewrites /api/* to Render and other paths to index.html; trailingSlash is false. | Refresh /student, /client, and /project/:id on deployed host and test trailing slash. | Existing rewrite appears correct in both root and frontend vercel.json; hosted behavior unverified. |
| Invalid input, oversized upload, malformed GitHub URL, rate limits, server errors | Request body is globally bounded; Multer limits file size and filters extensions; import endpoint calls GitHub. | Submit oversized/malformed requests and check 4xx responses without stack/secret leakage. | 2 MB JSON bound, import URL validation and timeout added; full upload MIME/content validation remains limited. |

## Verified configuration and test limits

- .env is ignored by Git; the local backend/.env exists, but its contents were deliberately not inspected. No root .env exists.
- npm ci completed for root and backend from the committed lockfiles. npm audit fix reported zero vulnerabilities for both dependency trees; the final root and backend audit summaries each show total 0.
- npm run build passed (Vite transformed 1,710 modules; build completed in 26.38 seconds). npm --prefix backend run test:security passed all 6 signature/provider/webhook checks. test:payment-flow, test:security-chat, and test:runtime each passed using the isolated local test database and explicit non-production mock provider.
- There is no configured browser E2E harness. A local browser check was attempted, but Windows computer use stopped because it could not determine the current browser URL with enough confidence. Therefore responsive layout, browser console, and real test gateway UX were not verified here. Local mock results are not evidence of Razorpay production behavior.
- Recent history confirms the latest commit message explicitly added the simulated-signature bypass (a3bce22). The prior pasted report's claim that a random JWT fallback had previously been removed does not match source at audit time.
